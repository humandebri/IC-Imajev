# IC-Imajev：4B判断モデルのcanister実装と、update／queryによる全層推論

こんにちは。Imajev-4Bのテキスト判断経路をInternet Computer上に実装した、**IC-Imajev**を紹介します。

- [アプリ](https://imajev.kinic.xyz/)
- [推論canister：IC Dashboard](https://dashboard.internetcomputer.org/canister/xis3j-paaaa-aaaai-axumq-cai)

このプロジェクトでは、**Qwen3.5-4B＋判断用LoRA＋専用readoutの全32層を、canister内のRust/Wasmランタイムで計算**します。外部の推論APIへの委譲は行いません。入力の抽出・token化はclient側で行います。

Imajevは、証拠と質問・選択肢を入力し、選択肢を直接スコア化するモデルです。最後の判断位置のhiddenから専用readoutでスコアを計算するため、自由な文章生成や、その生成結果を分類する処理を必要としません。

現在はテキスト判断経路を対象としており、画像encoderは使用していません。

## モデルとランタイム

モデルは32層で、24層のlinear attention／Gated DeltaNetと、8層のfull attentionから構成されています。

基盤の重みと投影入力にはINT8演算を使い、LoRAとreadoutはF32で計算します。テキスト経路の重みpackは約**4.70 GB**です。LoRAはrank 64・alpha 128、readoutは256×2,560のF32行列で、入力された選択肢に対応する行を評価します。

Rust/Wasmランタイムには、量子化された積和に加えて、RMSNorm、SiLU、partial RoPE、causal convolution、attention、Gated DeltaNetの状態更新、final norm、readoutを実装しています。

重みpackの容量と、実行時のheap使用量は別の値として管理しています。また、INT8化によって元の未量子化モデルとは数値計算が変わるため、後述するbit一致は採用した量子化経路での比較です。

## update推論の仕組み

主軸となるupdate経路では、推論canisterが中間状態を保持し、全32層の計算を最後まで進めます。

全層の計算を1回のupdateに収めるのは難しいため、命令予算に合わせて複数の処理単位に分割しています。各処理単位を実行する内部関数をworkerと呼び、canisterから自分自身へのupdate呼び出しで順に実行します。workerが計算した途中の状態をcanister内に保持し、次のworkerがその続きから再開します。最後にfinal normとreadoutを計算して、判断結果を返します。

```text
推論の受付
    ↓
worker 1：計算 → 中間状態を保存
    ↓ 自己呼び出し
worker 2：保存状態から計算を継続
    ↓
…
    ↓
final norm / readout → 判断結果
```

この方式では、内部の計算が複数のupdateに分かれます。外部からの呼び出し回数が1回でも、内部workerの実行・通信費用は発生します。継続処理にtimerは使用しません。

ローカルICの実canister間呼び出しでは、BOOM DAO由来の3入力について、内部worker **5／4／5回**で推論が完了しました。以前の9回測定では、最大worker handler命令は約358.7億、最大heapは4,234,608,640 bytesで、40B命令・4 GiBの上限内でした。

この測定は以前のprefix構成によるものです。現行のupdate経路は固定27-token prefixを使用しており、過去のworker数を現行構成の性能値として流用していません。

## query推論の仕組み

通常queryでは、clientが計算を順に呼び出し、中間状態を次のqueryへ渡します。

持ち回る状態には、hidden、attention K/V、DeltaNetのrecurrent state、演算途中の値などが含まれます。model・pack・input・進捗・checksumを照合して、別入力や別の重みの状態を混ぜないようにしています。

update経路ではcanisterが中間状態と継続処理を管理し、query経路ではclientが管理します。後述の32／50 queryという測定は、この通常query経路の結果です。

## update APIの利用方法

別のcanisterから、cyclesを添付して都度払いで推論を依頼できます。

1. 対応するtokenizerで入力をtoken化し、token IDsと選択肢を用意します。
2. `quote`で必要なcyclesと料金版を取得します。入力形状と料金設定が同じなら、見積もりを再利用できます。
3. token IDs・選択肢・request ID・料金版を指定し、必要なcyclesを添付して`infer`を1回呼び出します。
4. 同じ呼び出しの応答として、最終的な判断結果を受け取ります。

呼び出し側で中間状態を保存したり、推論を継続するために何度もAPIを呼んだりする必要はありません。通常推論ではstatus pollingも不要です。

現行の入力範囲は、**固定27-token prefix＋1〜57-token suffix、全入力28〜84 tokens**です。

支払い処理には、必要cyclesだけの受領、余剰返却、request IDによる再送時の二重課金防止、worker失敗時のサービス料金返金を実装しています。公開canisterの有料update受付は現時点では停止中です。

## IC向けに行った最適化

大きく分けて、重みの読み出し、数値演算、状態転送、呼び出しへの配置を最適化しています。

|対象|実装した最適化|
|---|---|
|固定重み|復元・検査・cache配置を準備updateへ移し、推論時は準備済みデータを参照|
|積和|block256のINT8 dot、Wasm SIMD、token・出力間での重みロード共有|
|共通計算|入力量子化・scale・LoRA A積・RoPEなどを再利用|
|prefix|同じ先頭token列を全層で事前計算し、suffixから再開|
|状態転送|BF16/F32値の可逆codecと圧縮packet|
|実行配置|MLP・Delta・Attention・残差／normを融合し、層をまたいで仕事量を配分|
|終端処理|最後の判断位置に不要な演算・中間返信を省き、readoutまで接続|

prefixは要約ではありません。同じ先頭token列について、hiddenやK/V、DeltaNet状態を計算済みにし、その状態から続ける仕組みです。

また、INT8量子化と可逆通信圧縮は分けて扱っています。通信圧縮・計算再利用・融合については、採用済みの量子化方式に対する数値一致を検証しています。

## BOOM DAO proposal 161件を対象にした評価

検証対象は、BOOM DAO proposal **#500〜#660の全161件**です。保存したsnapshotを使い、全件について変更内容と必要な証拠を確認し、モデル判定・追加確認・対象外のいずれかへ振り分けました。過去の採決結果や正解ラベルはモデル入力に含めていません。

テストしたのは、proposalを受け取り、変更前後の情報を抽出し、canister内でのモデル推論とアプリケーション側のチェックを経て最終判定を返す評価パイプラインです。全161件を入力しましたが、161件すべてでモデル推論を実行したわけではありません。

処理の流れは次の通りです。

1. snapshotの構造と変更内容を確認し、数値と単位を抽出します。モデル対象については、構造化された新しい値と表示内容、変更項目の保持を照合しました。旧値は履歴renderingから取得しており、当時のchain stateとの独立照合はしていません。
2. 資金移動や実行callに必要な証拠が不足・矛盾していれば、モデルへ推測させず追加確認へ回します。
3. 最低stake・最低投票lockを直接扱う数値判定は、変更前後の値と単位を保持してモデル入力を作ります。質問・選択肢・chat template込みで128 tokensを超える場合は、変更内容を切り捨てず停止します。
4. モデルの選択肢スコアに閾値を適用し、Tool側のチェックと合わせて最終判定を出します。

その結果、50件をモデル推論へ、23件を推論前の追加確認へ、88件を現在の評価方針の対象外へ振り分けました。モデルの直接判定は数値上の参加条件に限定しており、proposal全文の意図や実行コードまで評価した結果ではありません。

50件は数値入力として18種類にまとまりました。同じ数値入力は1回の推論を共有していますが、proposalの意図まで同じとみなしているわけではありません。

2026年10月7日のローカル評価では、prefix状態を新規に準備し、保存済みの判断結果を再利用せずに全層推論を実行しました。

|項目|結果|
|---|---:|
|異なるモデル入力|18種類|
|全入力長|67〜128 tokens|
|32-query経路|7入力|
|50-query経路|11入力|
|推論query合計|774回|
|以前の同じ入力の推論query合計|3,703回|
|今回のprefix・codec準備|990 query|
|準備＋成功推論|1,764 query|
|前回とのraw logits比較|18入力すべてbit一致|

例えば、**#617はprefix 38＋suffix 59＝97 tokensを32 query**で、**#505はprefix 48＋suffix 80＝128 tokensを50 query**で処理しました。

入力長だけでなく、再利用できるprefixとsuffixの長さが実行経路に影響します。したがって、任意の128-token入力を32 queryで処理できるという結果ではありません。

各推論queryについて、handler命令50億未満、Candid要求・返信各200万bytes未満、記録されたheap 4 GiB未満を確認しました。重みuploadと固定準備updateの費用は、表のquery数に含めていません。

## proposalの判定基準と結果

最終判定は、`approve`を通過、`reject`と`hold`を停止・追加確認とする方針です。

- **approve：** 今回扱う数値上の参加条件について、通過と判断したもの。
- **reject：** モデルがreject側を選び、A/B差から算出したスコアが閾値以上のもの。
- **hold：** スコアが閾値未満、必要な証拠が不足・矛盾、直接判定の範囲外、または入力予算を超えたもの。
- **対象外：** Motion、表示・brandingのみの変更、抽出上変更なしなど、現在の選別方針で評価から除外したもの。承認としては扱いません。

全161件の結果は次の通りです。

|最終結果|件数|判定元・理由|
|---|---:|---|
|approve|2|モデル判定と数値参加条件のチェックを通過|
|reject|10|モデルのreject側スコアが閾値以上|
|hold|38|モデルのA/B差から算出したスコアが閾値未満|
|hold|17|最低stake・最低投票lockの直接判定範囲外|
|hold|5|資金移動・mint・実行callの証拠不足や矛盾|
|hold|1|全変更を保持すると128-token予算を超過|
|対象外|88|現在の選別方針では評価しない|
|合計|161|approve 2、reject 10、hold 61、対象外88|

モデルのreadoutはA／B／unknownのlogitsを返します。今回のハーネスではraw A/B差から `sigmoid(abs(logit_A - logit_B))` を算出し、0.6を閾値にしています。これは未校正のスコアで、判定が正しい確率を表すものではありません。`hold`も内部unknownを直接採用したものではなく、スコア閾値とTool側のチェックによる結果です。

### 判定の具体例

**#562と#566：大幅な参加条件の引き上げでも、モデルの方向だけでは通過させない**

最低stakeを5から100万tokensへ、最低投票lockを2日から1,461日へ変更する入力です。モデルのA/B出力は弱くapproveを支持しましたが、スコアは約0.5354で閾値0.6を下回り、最終結果はholdになりました。#587と#588でも、モデルがapprove側を選んだ一方で、閾値によりholdとなりました。

モデル対象50件について元proposalと照合したエージェントレビューでは、大幅な参加制限の強化と分類した32件はreject 10件・hold 22件で、今回の通過方針ではすべて停止側でした。この分類は人間による正解ラベルではなく、一般的な危険検出率を示すものではありません。

**最低投票lockが1日から2日になる16件：変更の方向と危険性を区別する**

これらはすべてholdでした。条件が厳しくなる変更ですが、その事実だけで危険と断定する基準はないため、危険を正しく検出した件数には含めていません。

**#656と#659：参加条件の改善を通過させるが、proposal全体の安全性とは分ける**

#656は最低stakeを1,500万から5 tokensへ引き下げ、投票期間を1日から3日へ延長します。#659は最低stakeを1,500万から5 tokensへ引き下げ、最低投票lockを2日から1日へ短縮し、lock bonusを1%から100%へ変更します。両方とも最終結果はapproveでした。

ただし、#656の説明にあるtakeoverへの言及は数値入力に含めておらず、#659のbonus変更が投票力配分に与える影響も未評価です。approveは数値上の参加条件チェックの通過を意味し、proposal全体の承認ではありません。

**資金移動・mint・汎用callの5件：証拠がなければ推論前に停止**

3件のtreasury transfer、1件のmint、1件の汎用callはholdでした。受取先の管理主体、残高、供給量などの必要情報がなく、汎用callでは構造化payloadと表示内容の不一致も確認しました。

**#585：入力に収まらない変更を削除しない**

全変更を保持すると130 tokensとなり、128-token予算を超えました。このため、一部を落として判定するのではなく、モデルを呼ばずholdにしています。

今回のテストでは、全161件の処理経路と理由を記録し、そのうちモデルを実行した18種類の入力で全32層の実行と数値再現性を検証しました。投票や自動停止は実行していません。

今後は、update経路を中心に、canisterからの組み込みやすさ、入力範囲、実行費用を検証していきたいと考えています。モデル実行の分割方法や、固定選択肢の判断をcanisterの処理へ組み込む用途について、フィードバックをいただけるとうれしいです。
