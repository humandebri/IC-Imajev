# S2の共通変換・復元を再利用する探索

2026-10-03。毎回繰り返す演算の除去を目的に、元容量INT8のS2候補を3通り実装した。全候補は独立したローカル診断canisterだけで検証し、全モデルの採用候補へは接続していない。

S2はrank49の整数積で4×4ブロックを計算する。raw版は最初のtoken群で固定重みの係数を作り、後続tokenで使い回す。lane版は4出力群をSIMDの4laneへ対応させ、スカラー水平和を除く。factored版はさらに入れ子の重み変換と出力復元の共通部分を一度だけ計算する。49個の重み係数、16個の復元式の記号的同値とI32上限をgenerator内で検証する。F32のblock256の丸め・積和順序は維持した。

主入力87 token・layer3 Q、8192×2560の同一module内比較。現行raw S1は入力準備1,862,494、投影992,676,612、合計1,004,100,928命令。

共通変換の再利用はS2内部では改善したが、いずれも現行S1より命令が増えるため未採用。5実入力と6境界入力、各3方式の33通常queryで全出力digestはnative参照と一致した。これはQ投影の検証で、全モデルの判断精度・query数の検証ではない。診断はoriginal・旧pair・S1・S2を同時保持しており、候補単体のINT8 payloadは元容量でも、全モデル4GiB配置を証明するものではない。

残る増加は投影本体が支配的。lane版の主入力ではS1比、入力準備+5,653,562に対し投影+143,606,902命令。係数入力のload数・変換・復元の増加が原因候補だが、各SIMD命令の寄与を分離測定した結果ではない。積の回数だけから命令削減を見積もらない。

証拠は `artifacts/wat_s2_{raw,lane,factored}/check/report.json`、各`validated-source.zip`。固定重みを65 updateで準備し、質問依存処理は通常queryに課金した。module hashを前後で照合し、ソースを固定した。生成物はignore。
