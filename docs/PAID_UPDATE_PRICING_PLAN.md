# 都度払い料金の校正計画

2026-10-06。下記は詳細な校正計画。ユーザーの「POCなので厳密でなくてよい」という指定に従い、測定を6形状へ絞ったPOC版を実行し、基本10B＋suffix tokenごと3B cyclesへ調整してローカルで検証した。[結果と設定](PAID_UPDATE_PRICING_POC.md)を参照する。常駐維持費の厳密な配分・採算検証・本番配備は今回の範囲に含めない。

## 方針

利用者canisterがcyclesを添付して外部`infer`を1回呼ぶ方式を維持する。入力形状から事前に料金を確定し、成功時はその額を徴収する。前払い残高や成功後の差額精算は導入しない。余剰添付は未受領で返却し、運営側の推論失敗は受領料金を全額返金する。呼び出し元自身の実行・通信費は別である。

現在の`100B + suffix_tokens * 3B`は支払い検証用で、本番価格の根拠にはしない。モデル・演算順序・34B付近のworker分割・対応入力範囲は料金校正のために変更しない。

## 1. 測定条件と費用の分離

- 対象module、model、prefix、料金設定、subnetと料金パラメータを記録する。既存の最終通常版と対応するビルドを固定し、必要な診断変更は別artifactに保存する。
- localの比較canisterをsnapshotで保護し、測定後はmodule・重み・prefix cacheを復元する。default canisterを変更しない。mainnet測定・配備は後続段階とする。
- 呼び出し元の支払額と、推論canisterが消費する費用を別々に記録する。推論側の前後残高に受領額・返金・外部入出金を照合し、予約cyclesへの移動も確認する。残高差をそのまま純粋な実行費とは扱わない。
- worker命令、入口・callbackの処理、内部呼び出し、通信bytes、heap、実行時間を記録する。worker counterだけでは全費用を網羅しない。
- 推論前後にidle区間を測り、メモリ維持費と監視操作の費用を区別する。期間中は他のjob、top-up、cache準備、snapshot操作を混在させない。必要な管理照会の費用は別途記録する。
- 料金表に基づく計算と残高差を突き合わせ、説明できない差を報告する。localの観測だけでmainnetの実費を確定しない。

## 2. 入力長を変えた測定

共通27-tokenと投票38-tokenの両prefixについて、suffix長1・8・16・32・48・57の12形状を測る。計算費用の測定入力はAPIの制約を満たすtoken列として固定し、質問回答の精度評価とは区別する。

まず各形状で異なるtoken列を2件ずつ、計24推論を測定する。次に各形状の追加入力1件、計12件を保留評価用に実行し、料金係数の決定に使った入力と分ける。選択肢数の小さいケースと上限7件、prefix選択境界、workerが増える境界を追加する。差や不安定な費用が出た形状だけ反復を増やす。既存のBOOMDAO 3入力も回帰確認に利用する。

最大入力でworker上限6、各worker 40B命令未満、heap 4GiB未満を確認する。現在のheap余裕が小さいため、大きな計測bufferや並行sessionを導入しない。

## 3. 料金係数の決定

初案は現行APIで表現できる`base_fee + fee_per_token * suffix_tokens`を使う。

1. 計算費用の測定から、全ての測定形状を覆う基本費用・token単価を求める。平均への単純な当てはめでは短い入力や境界で赤字になる可能性があるため、測定上限との差も確認する。
2. 運営余裕は計算・通信費に対して暫定20%を候補とし、失敗時の計算・全額返金費用の測定を見て調整する。有限の測定に基づく余裕であり、全入力への保証とは表現しない。
3. 維持費は、実際の常駐メモリの1日分を想定成功件数で割って基本料金へ配分する。10・50・100件/日の収支を比較し、必要な損益分岐件数を示す。利用ゼロの維持費まで都度課金で回収できるとは扱わない。
4. 未使用入力で料金が測定した変動費を下回らないか検証する。prefix間で大きな価格差が必要な場合は、共通式による割高幅を示してからbank別の係数を検討する。最初からAPIを拡張しない。

receiptは現在128件・24時間保持なので、件数上限を超える売上を現行仕様で見込まない。より高い利用件数への対応は別の容量改善として扱う。

価格、維持費配分、余裕率を分けて報告し、利用者には合計した確定料金を提示する。subnetの変更やruntimeの変更後は再校正する。金額は測定後に決め、現時点で具体的な値を本番価格として固定しない。

## 4. 設定・実装と検証

共通線形式で十分なら、owner専用の`configure_paid`で係数と料金版を更新するだけに留める。係数の算出根拠を報告に保存し、quoteとinferは引き続き同じ式を用いる。

bank別料金が必要な場合のみ、Config・quote・stable metadata・Candid・caller例を変更し、旧metadataからの移行を検証する。既存receiptには受付時の料金を保持し、後の料金変更で既存の返金額を変えない。

確認項目は、quoteと受領額の完全一致、余剰添付の返却、不足・古い版・Busy・不正入力の受領ゼロ、保持中の同一request再送の二重課金防止、失敗時の全額返金と二重返金防止、既存receiptのupgrade保存。料金変更だけで演算結果が変化しないことも既存3入力で確認する。過去の検証artifactを上書きしない。

reserveは販売料金と分けて設定する。凍結費用を差し引いたliquid balanceに対し、最大対応jobの計算費用、未解決返金、運営余裕を維持できるか確認する。現在のreserve 2Tを無条件に本番へ流用しない。

## 完了条件と成果物

- 費用の内訳と未説明差、測定入力・module・subnet条件が再確認できる。
- 測定用・保留評価用の全入力を完走し、料金が測定した変動費を覆い、維持費込みの損益分岐が示される。
- 新料金でも外部1 update、命令・heap上限、元出力との一致、支払い・返金の既存保証を維持する。
- 測定スクリプト、raw応答、独立検証、料金係数の算出結果、本番候補設定、利用件数別の収支表を新しいartifactと測定報告へ保存する。

この段階で確定するのは測定条件に基づく本番候補料金である。mainnetへの反映は対象subnetの確認と配備判断を経て行う。
